# Documentation guide

The documentation is organized by project lifecycle. The original technical dossier is the reference baseline; the Markdown documents below make the work easier to review, discuss, test, and maintain.

## Structure

- `reference/`: unchanged source dossier and notes about its status.
- `discovery/`: truthful project origin, problem statement, and needs analysis.
- `specifications/`: requirements, use cases, and acceptance criteria.
- `design/`: architecture and data model.
- `planning/`: implementation increments.
- `testing/`: test strategy and traceability.
- `collaboration/`: roles, workflow, decision records, and meeting notes.

## Documentation rules

1. Keep the original PDF unchanged.
2. Do not copy the entire PDF into multiple Markdown files.
3. Refer to requirement identifiers (FR-01, UC-01, etc.) when discussing scope.
4. Mark proposals as proposals until the team/client validates them.
5. Record scope changes and decisions with dates and rationale.
6. Never invent user interviews, client statements, meeting outcomes, test results, or individual contributions.
